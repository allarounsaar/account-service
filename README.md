# Bank Account Service

A small core banking service: accounts, balances, transactions, and an
event feed published to RabbitMQ for other consumers.

## Tech stack

Java 25, Spring Boot 4, MyBatis, Gradle, Postgres 18, RabbitMQ, JUnit 5 +
Testcontainers.

## How to build and run

### Option 1 — everything in Docker
Prerequisites: Docker + Docker Compose
```bash
docker compose up --build
```

This starts Postgres, RabbitMQ, and the application together. The app runs
database migrations (Liquibase) automatically on startup. Once it's up:

- OpenAPI Specification: [http://localhost:8080/v3/api-docs](http://localhost:8080/v3/api-docs)
- Swagger UI: [http://localhost:8080/swagger-ui.html](http://localhost:8080/swagger-ui.html)
- RabbitMQ UI: [http://localhost:15672](http://localhost:15672) (Credentials: `guest` / `guest`)

### Option 2 — run the app locally, infra in Docker
Prerequisites: Java 25, Docker (for dependencies).
```bash
docker compose up postgres rabbitmq
./gradlew bootRun
```

### Running tests

```bash
./gradlew test
```

Integration tests use Testcontainers, which starts its own throwaway
Postgres/RabbitMQ containers automatically — no manual setup needed, but
Docker must be running.

### Test coverage report

```bash
./gradlew test jacocoTestReport
```

Report is written to `build/reports/jacoco/test/html/index.html`.

## API overview

| Method | Path | Description |
|---|---|---|
| POST | `/api/accounts` | Create an account with balances in supported currencies `EUR`, `SEK`, `GBP`, `USD` |
| GET | `/api/accounts/{accountId}` | Get an account and its balances |
| POST | `/api/accounts/{accountId}/transactions` | Create a transaction (IN/OUT) |
| GET | `/api/accounts/{accountId}/transactions` | List transactions for an account |


## Important design decisions

**Layered architecture.** The codebase is structured by feature/domain (`account`, `transaction`, `outbox`) with a clear layered separation inside each domain:
Considered CQRS/CQS at first, but for four endpoints it added more complexity than value — a feature-packaged layered structure is easier to review without unnecessary architectural overhead. .

**Primary keys are UUIDv7**, generated by Postgres 18's built-in
`uuidv7()` function. Chosen over UUIDv4 because v7 is time-ordered, which
keeps index inserts sequential instead of scattered randomly (better insert/index performance than v4), while still being
non-sequential/non-guessable from outside.

**Monetary precision and storage.** The API accepts monetary amounts with up to 2 decimal places (strictly validated) and formats responses to 2 decimal places using `HALF_EVEN` rounding. In the database, monetary values are stored with 4 decimal places (`NUMERIC(19,4)`) to maintain precision and avoid rounding errors during financial calculations.

**Balance concurrency uses `SELECT ... FOR UPDATE`.** When a transaction
debits or credits a balance, the row is locked for the duration of that
one request, so two concurrent transactions on the same account/currency
can't race and corrupt the balance.

**Outbox pattern for RabbitMQ publishing.** Writing to Postgres and
publishing to RabbitMQ cannot be done atomically as two independent actions without risking dual-write inconsistencies (e.g. database commit succeeds but message publishing fails). Instead, domain mutations insert events into `outbox_event` within the same active database transaction.
A background scheduler polls pending events using `SELECT ... FOR UPDATE SKIP LOCKED`, 
publishes them to RabbitMQ (`bank.events` topic exchange), 
and handles retries with exponential backoff.

**Integration Testing** run against temporary PostgreSQL and RabbitMQ instances using Testcontainers.



## Transaction throughput estimate

The transaction endpoint `POST /api/accounts/{id}/transactions` was tested with **k6** using a single account. 
All requests updated the same balance row, so they had to wait for the `SELECT ... FOR UPDATE` lock.

### Test machine
- AMD Ryzen 7 5700X — 8 cores / 16 threads
- 32 GB RAM
- NVMe SSD
- Linux x86_64
- Spring Boot + PostgreSQL + Docker + k6 running on the same machine

The application, PostgreSQL, Docker containers, and k6 load generator were all running on the same home PC.

### Test results

| VUs | Duration | TPS | p95 latency | Errors |
|---:|---:|---:|---:|---:|
| 1 | 1 s | ~162 | ~6.6 ms | 0% |
| 10 | 10 s | ~115 | ~297 ms | 0% |
| 20 | 10 s | ~136 | ~358 ms | 0% |
| 40 | 20 s | ~139 | ~548 ms | 0% |

The 1 VU test shows that without significant contention, a request takes only about **6 ms**. As more concurrent requests target the same account, the row lock becomes the main bottleneck. Throughput reaches about **140 TPS**, while latency continues to increase.

Based on these tests, **~140 TPS is a reasonable estimate for a single account** on this machine.

For multiple accounts, requests can update different balance rows concurrently, so the single-row lock is no longer the main bottleneck. Based on the ~6 ms low-contention latency, the default HikariCP pool of around 10 connections, and the available hardware, a rough multi-account estimate is **~1,000–1,500 TPS**.



## Horizontal Scaling Considerations
- The application is stateless and scales horizontally behind load balancer (e.g., NGINX).
- Outbox publisher uses `SKIP LOCKED`, allowing multiple application instances to consume and publish events in parallel without conflicts.
- The balance row is the real bottleneck. Adding more app instances doesn't help when one account is very busy, because `SELECT ... FOR UPDATE` locks that account's balance row. If one transaction is updating it, the other transactions have to wait until the first one finishes. So adding more app instances mainly helps when the traffic is spread across many different accounts, rather than when lots of requests are trying to update the same account at the same time.
- The database can become the bottleneck when adding more app instances.
  Each instance's connection pool adds up against Postgres max connections limit. Read replicas can help with this by handling the GET requests
- The tables (mostly transaction) will keep growing as the application writes more data, 
  which can eventually affect storage, query performance, and maintenance; partitioning or archiving old rows might be one solution. 
 
## Use of AI
AI (Claude/ Gemini/ OpenCode agent) was used throughout this project as a design and coding
assistant — for working through architecture and schema tradeoffs (e.g.
locking strategy, design patterns, DTO/naming conventions), TPS estimation and for
generating boilerplate (MyBatis mappers, Liquibase changesets, exception
handling, test setup). All resulting code and design decisions
were reviewed, understood and adjusted before being included.
Most business logic and initial setup was done manually, without AI.
